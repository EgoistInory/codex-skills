# 番茄小说通用工作流

## 定位

用于把一个网文项目按“事实源 -> 续写 -> 审校 -> 状态更新 -> 投稿导出”的方式稳定推进。它是流程编排 skill，不绑定具体书名、仓库、人物或剧情。

如果项目内存在更具体的 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、书籍说明或用户指令，先遵守更具体的项目规则。

## 推荐项目结构

优先识别现有结构，不为了套用本 workflow 重组目录。若从零搭建，可采用：

```text
<project-root>/
├── AGENTS.md
├── books/
│   └── <book-name>/
│       ├── PROJECT_BRIEF.md
│       ├── CURRENT_STATUS.md
│       ├── HANDOFF.md
│       ├── 正文/
│       ├── 大纲/
│       ├── 设定集/
│       ├── 投稿包/
│       ├── scripts/
│       ├── .webnovel/
│       └── .story-system/
```

可替换为单书结构；关键是把正文、设定、大纲、状态、审查记录和导出物料分开维护。

## 入口步骤

1. 从项目根开始，先读项目协作规则，例如 `AGENTS.md`。
2. 确认目标书籍目录；多书项目必须先确定是哪一本。
3. 检查工作树状态，识别用户已有改动，不回滚、不覆盖无关文件。
4. 在目标书籍目录内执行写作、审校和导出命令；在项目根执行 Git 命令。

## 必读上下文

续写、审校或更新状态前，按需读取：

1. 项目简介：`PROJECT_BRIEF.md` 或同类文件
2. 当前状态：`CURRENT_STATUS.md`
3. 交接记录：`HANDOFF.md`
4. 总纲、卷纲、章纲
5. 相关设定：世界观、角色、力量体系、势力、时间线、伏笔表
6. 机器状态：`.webnovel/state.json`、`.story-system/MASTER_SETTING.json` 或同类文件
7. 最近 1-3 章正文
8. 当前章节对应章纲

若旧聊天记录与项目事实源冲突，以项目文件为准。

## 总目标与三道门

目标不是简单“把章节写完”，而是稳定完成一部长篇网文：主线清晰、人物有魅力、爽点持续、设定闭环、章节有追读欲，避免太监、烂尾、流水账、设定堆砌、剧情空转、人物扁平、文风廉价和明显 AI 味。

执行时把任务分成三道门：

1. **正文生产门**：专门负责高质量章节正文。正文必须是小说场景，不是大纲、总结、剧本、设定表或写作说明。
2. **质检门**：专门检查流水账、AI 味、爽点不足、人物扁平、空洞表达、机械模板、无钩子、无变化。
3. **设定一致性门**：专门维护人物、金手指、伏笔、时间线、世界观、能力边界和已发布事实。

三道门都通过后再交付。若发生冲突，优先级为：不破坏设定一致性 > 不交付低质量正文 > 局部文句好看。

## 续写流程

1. 明确下一章章号、标题、视角、场景、冲突目标、信息揭示边界和章末钩子。
2. 对照章纲和设定，列出本章必须推进、禁止提前揭露、禁止改写的内容。
3. 选择本章至少两个功能：推进主线、制造危机、兑现小爽点、埋伏笔、改变人物关系、展现能力成长、增强世界观吸引力、留下章末期待。
4. 写入 `正文/NNN-标题.md` 或项目约定路径。扩展名可为 `.md`，但正文内容必须是投稿兼容纯文本。
5. 单章按目标平台节奏控制长度。番茄常见发布源文建议不少于 2,000 中文字符，项目可设更高目标。
6. 每章形成“开头有钩子，中段有冲突，后段有变化，结尾有期待”的阅读体验。
7. 每章保留即时冲突、可感知收益或规则反制，并留下能推动下一章的问题。
8. 不为了单章爽点破坏能力代价、人物边界、时间线或后续高潮。
9. 若某段只是交代信息、没有场景、没有情绪、没有冲突、没有吸引力，主动重写，不交付低质量正文。
10. 完章后同步更新状态、审查记录、交接文件和必要的机器状态。

## 正文生产约束

正文必须像真正可发布的网文小说正文：

- 用场景承载信息。禁止把正文写成设定说明书、剧情摘要、作者分析或任务清单。
- 每个场景都要有目标、阻碍、冲突、变化和余味，不能只用“然后、接着、随后、过了一会儿”串事件。
- 爽点要具体：先有压迫、误解、轻视、危机或不甘，再有铺垫、反击、兑现和余波。
- 高级感来自准确表达：精准动词、清晰画面、情绪递进、人物选择和有力量的细节；不要靠生僻词、华丽辞藻或长句堆叠。
- 环境描写要服务情绪、压迫感、人物处境、剧情推进或氛围营造，不做无关背景板。
- 心理描写要呈现犹豫、欲望、恐惧、挣扎、执念、误判和选择，不只替人物解释答案。
- 动作描写要有因果和节奏：写动作如何发生、身体如何发力、对方如何反应、环境如何被影响。
- 章末悬念要自然来自剧情压力、人物选择、秘密揭露、危机升级、反派行动、能力异变或情绪爆点，不机械断章。

## 反模板化与人物细节

写作时避免把网文节奏写成固定模板、范式化句群或空洞判断。爽点、钩子和情绪波动必须落到可观察的角色选择与场面细节上。

### 开场与时空锚点

不要每章都用“时间 + 地点 + 事件说明”的固定开场。时间和地点可以保留，但优先嵌入场景运动：

- 用天气、光线、声音、气味、人群、物件状态或人物正在做的动作带出场景。
- 时间锚点服务压力，例如倒计时、疲劳、营业时间、门禁、病人状态、手机消息，而不是单独报时。
- 地点锚点服务冲突，例如谁能进门、谁站在门外、谁被隔在玻璃后、哪个监控死角暴露问题。
- 连续章节要变换开场姿态：动作开场、对话开场、环境开场、人物身体状态开场、证据物件开场、异常现象开场轮换使用。

### 人物鲜活感

每章至少让关键人物出现可辨认的生活或心理细节，避免角色只作为剧情功能件移动：

- 主角需要有疲劳、饥饿、困意、伤痛、清洁、交通、等待、失眠、短暂走神等生活消耗；长期高压剧情也要写恢复失败或身体透支。
- 重要人物出场时补足表情、眼神、停顿、语速、手部动作、站位、衣物状态或小习惯。
- 写心理活动时用“他为什么此刻不能说/不敢信/必须退一步”替代抽象情绪标签。
- 关系变化要落实到微动作：是否让路、是否递东西、是否避开称呼、是否压低声音、是否改变站位。
- 配角不要只负责提供信息；让他们有自己的顾虑、专业边界、利益损失或情绪反弹。

### 异能与规则刻画

异能、金手指和修行规则不能只作为解题按钮出现。每次关键使用至少写清一到两项：

- 来源：能力从哪里来，为什么属于主角，是否有历史、秘密、限制或代价。
- 感官表现：视野、听觉、触感、痛感、温度、颜色、符号、噪声、眩晕或身体反应。
- 操作边界：能看见什么、看不见什么、不能越过谁的同意、不能替谁做决定。
- 代价与恢复：消耗信任、体力、记忆、关系、时间、伤口、睡眠、冷却或后续判断力。
- 成长变化：升级解锁了什么，也带来什么新认知、新限制或新危机。
- 创造性用法：主角如何组合、逆用、借势或在限制下使用，而不是单靠能力碾压。
- 外部反馈：旁人看到什么、误解什么、害怕什么，或者因此改变对主角的态度。
- 剧情价值：能力要推动剧情、制造冲突、改变关系、引出敌人、揭开秘密或塑造命运。
- 失败与残缺：能力可以给方向，但不要总给完整答案；残缺信息更利于制造下一章钩子。

优先采用：

- 用具体证据、动作、物件、时间点、身体反应和对话潜台词承载剧情推进。
- 让人物用自己的利益、恐惧、职业习惯、关系边界和既往经历做选择，不用作者替人物下结论。
- 每个胜利写清代价、受影响的人、关系余波和下一步压力；不要只写“众人震惊”“局势逆转”“气氛凝固”。
- 每个配角至少承担一个具体功能：提供阻力、保留证据、误解主角、保护自身利益、提出专业限制或制造新问题。
- 情绪句之后补一个可见细节，例如手势、停顿、视线、文件编号、伤口变化、手机提示、病历曲线、旁人反应。
- 爽文结构可以使用，但每次兑现都要换成当前人物、场景和规则里的独有解法。

需要警惕：

- 固定段落顺序：挑衅 -> 打脸 -> 全场震惊 -> 反派放狠话。
- 固定开场顺序：先报时间地点，再解释当前任务，再让角色入场。
- 抽象评价堆叠：很强、很冷、很痛、很震撼、所有人都明白了。
- 空泛主题句：这就是规则、这就是代价、这就是现实，除非紧接着有具体事件支撑。
- 人物工具化：配角只负责解释设定、送线索、被打脸或无条件相信主角。
- 同质化台词：所有角色都用同一种短句、反问、冷笑、网络梗或作者腔。

## 设定一致性约束

写作和修订必须维护项目事实源：

- 人物一致性：主要人物的欲望、弱点、执念、恐惧、秘密、底线、成长轨迹和行为逻辑不能随剧情便利漂移。
- 主角主动性：主角要有目标、压力、底线、成长和选择，不能只是被剧情推着走。
- 配角独立性：重要配角要有自己的立场、利益、情感和选择；反派要有压迫感、行动逻辑和阶段性威胁，不能降智送死。
- 关系连续性：亲情、友情、爱情、合作、敌对、背叛、竞争等关系要通过事件、对话、误会、牺牲和选择累积，不靠标签说明。
- 金手指一致性：来源、表现、规则、限制、代价、成长和剧情价值要前后一致。
- 时间线一致性：日期、时段、行程、伤势恢复、睡眠消耗、事件先后和跨章状态要能对上。
- 伏笔一致性：新伏笔要登记去向；旧伏笔不能误提前揭底，也不能长期遗忘。
- 世界观一致性：规则、势力、地点、制度、资源和禁忌不能因单章爽点临时改写。
- 已发布正文优先：已发布或已审校正文是写后事实，修订只做最小必要改动。

## 正文格式

正文源文必须是纯文本小说正文：

- 禁止 Markdown 标题、加粗、斜体、引用、行内代码、链接、脚注和列表语法。
- 使用【】、「」、“”等中文标点表达系统提示、短信、契约字段、账簿内容或强调。
- 已发布或已审校正文只做最小修订，并同步记录原因。
- 批量替换或清理 Markdown 时，必须显式使用 UTF-8 读写，防止 `ã€`、`Ã`、`Â`、`�` 等乱码。
- 不把密钥、Cookie、后台截图隐私、平台登录信息写入正文、日志或交接文档。

## 质检约束

每章完成后至少检查，未通过则修订后再交付：

1. 字符数是否达到平台和项目下限。
2. 正文是否含 Markdown 标记、乱码、异常换行或投稿不兼容格式。
3. 时间线、地点、人物动机、称谓和关系是否一致。
4. 能力体系、代价、规则边界是否被突破。
5. 本章伏笔是否推进，是否误提前揭底。
6. 章末钩子是否指向下一章真实冲突。
7. 被修改 JSON、YAML 或状态文件是否可解析。
8. 是否出现固定模板化桥段、范式化句群或空洞表达。
9. 关键人物是否有独立动机、细节动作、关系边界和选择后果。
10. 爽点是否由本章独有证据、规则或人物行动触发，而不是靠旁白宣布。
11. 开场是否又落入固定“时间地点说明书”；时间地点是否嵌入了动作、环境或压力。
12. 主角是否出现生活细节或身体消耗，避免长期不睡、不吃、不累、不恢复。
13. 异能或金手指是否有感官刻画、边界、代价、失败残缺或外部反馈。
14. 是否出现流水账、设定堆砌、剧情空转、只铺垫不兑现、只对话不行动、只总结不场景化。
15. 是否存在廉价套路表达，例如“震惊全场”“倒吸一口凉气”“恐怖如斯”“无法形容”等空泛评价。
16. 是否有读者愿意继续看下一章的钩子，而不是仅仅完成信息交代。
17. 每章是否至少完成两个章节功能目标。
18. 反派和配角是否有有效行动逻辑，而不是无脑嘲讽、送经验或集体降智。

若项目提供审查脚本，优先运行项目脚本。没有脚本时，可用等价命令检查字符数、Markdown 标记、UTF-8 编码和状态文件解析。

## 番茄导出

日常续写不必每章导出 TXT。投稿、批量发布或用户明确要求时再导出。

推荐导出规则：

1. 从正文源文生成 `NNN-标题.txt`。
2. TXT 首行使用平台要求的章节标题格式，例如 `第N章 标题`。
3. 标题后保留空行，再写正文。
4. 导出前校验正文源文为 UTF-8、无 Markdown 标记、正文长度达标。
5. 导出失败时不要替换已有发布包，不标记为可发布。
6. 不替用户登录、上传或发布到任何第三方平台。

若项目已有脚本，例如 `scripts/export-fanqie.sh` 或同类命令，优先使用项目脚本，不手工绕过校验。

## 状态与交接

每次完成章节或关键审校后，更新最少必要状态：

- 当前章号、总字数或源文字符数
- 主角状态、地点、能力边界、代价
- 活跃剧情线、伏笔、下一章钩子
- 新增设定、人物关系变化、证据链或关键物件
- 审查结果、修订点、未解决风险
- 下一位协作者的第一步

状态文件要服务下一次恢复，不要写成泛泛总结。

## 可配合的小说 Skill

本 workflow 是主流程，不替代专项创作 skill。按剧情需要临时调用最合适的 skill；不要为了调用 skill 而改动项目结构、覆盖正文或生成无关目录。若专项 skill 的默认输出目录与当前项目约定冲突，先遵守项目约定。

- `webnovel-topic`：用于选题、市场向创意、金手指、核心卖点、受众定位和“一句话概念”打磨。
- `novel-generator`：用于从一句话方向或关键词快速扩展爽文提示词、雏形设定和章节草案；若它默认创建 `output/` 或 `.learnings/`，先确认是否适合当前项目。
- `webnovel-outline`：用于世界观、人设、分卷大纲、章节细纲和爽点排布规划。
- `webnovel-worldbuilder`：用于从零到完稿的一站式小说创作编排；已有成熟项目通常只在需要整体重建流程时使用。
- `webnovel-plan`：用于在既有项目中生成卷纲、时间线、章纲或增量设定，并写回项目记忆。
- `webnovel-query`：用于写前查询角色、设定、力量体系、伏笔、金手指状态和项目记忆。
- `webnovel-write`：用于实际续写、起草、扩写、重写或批量生成章节。
- `webnovel-review`：用于审查时间线、人物 OOC、设定冲突、伏笔回收、剧情 bug 和章节字数。
- `webnovel-polish`：用于文笔润色、节奏收紧、对话优化、爽点强化和“把这段写得更爽”。
- `webnovel-hot-memes`：用于男频/泛网文中的热梗、平台评论区、弹幕、短视频文案、轻喜剧反应和热门事件模板；只在角色、场景和时代适配时使用，避免过度堆梗。
- `webnovel-female-radar`：用于女频、言情、古言、现言、快穿、团宠、权谋、情绪流、人物关系和女性向平台语感。
- `webnovel-finalize`：用于完稿技术校验、错别字/标点/敏感词检查、平台格式适配和最终导出。

使用专项 skill 后，在最终回复中点明实际调用了哪些 skill，以及它们分别负责选题、爽点、热梗、续写、审查、润色、导出中的哪个阶段。没有实际调用时，只说明本 workflow 更新了这些可选配合时机。

## Git 与安全

1. 修改前查看工作树，避免覆盖用户已有改动。
2. 只提交或说明当前任务相关文件。
3. 同步前运行最相关验证，例如格式检查、状态解析、导出脚本或 `git diff --check`。
4. 不强推、不重写历史、不初始化嵌套 Git。
