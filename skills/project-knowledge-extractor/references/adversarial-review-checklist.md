# 独立技术评审与防幻觉十维核查门禁（Adversarial Self-Review Gate）

在生成项目知识档案后、正式向用户交付前，智能体必须切换为**独立技术评审者（Independent Technical Reviewer）**视角，对照源码执行以下 10 项强制核查，并将核查结论汇总至 `11_EVIDENCE_AND_GAPS.md`。

---

## 一、十维反事实与质量质询清单

### 1. 哪些结论没有代码证据？（Zero-Evidence Claims Check）
- [ ] **排查模型字段与枚举脑补**：文档中列出的每一个数据库字段、状态枚举值（如 `TaskStatus`、`DeviceStatus`），是否都与 ORM 源码逐字一致？（警惕将旧 `.sql` 文件中的残留列或通用常识状态如 `TIMEOUT/CANCELLED` 误写进 ORM 状态机）。
- [ ] **排查前端/边缘组件功能脑补**：文档描述的前端组件功能（如“解析某格式文件”、“导出某报表”），是否在前端源码中真实存在对应的解析函数或 API 调用？
- [ ] **排查阈值与配置键名脑补**：文档提到的超时时间（如 5 分钟 vs 180 秒）、重试次数、配置表 Key 名（如 `LARK_WEBHOOK` vs `LARK_WEBHOOK_URL`），是否与源码字面量完全一致？

### 2. 哪些关键功能仍停留在概念描述？（Conceptual-Only Gap Check）
- [ ] 是否不仅追踪了正向创建/执行链路，还完整追踪了**逆向控制链路**（单条取消、批量取消、强制终止、超时回收）的具体函数与行号？
- [ ] 是否明确记录了跨服务/跨仓库通信的**完整消息载荷契约（Payload Schema）**（如所有 MQ/Celery 发送的任务名、`args/kwargs` 字段结构、目标队列计算公式）？

### 3. 哪些模块的依赖关系尚未厘清？（Dependency Ambiguity Check）
- [ ] 当代码库中存在同名类（如两个文件都定义了 `Account` 模型）或新旧两套路由时，是否通过追踪 `import` 链条明确指出了哪一个是真实生效代码、哪一个是未挂载的废弃死代码？
- [ ] 控制器之间的横向调用、中间件对 CRUD 的调用是否已在架构图中完整体现？

### 4. 哪些架构图与代码实现不一致？（Diagram Drift Check）
- [ ] ER 图是否区分了**物理外键约束（Database ForeignKey）**与**应用层逻辑关联（Logical Join / `primaryjoin`）**？
- [ ] 状态机图中的每一条转换边（Transition Edge），是否都能在代码中找到对应的 `status = ...` 赋值语句？（严禁画出代码从未实现的自动状态流转边）。
- [ ] 系统拓扑图中的跨端口/跨服务调用，是否准确反映了同源代理（Nginx/Vite Proxy）与后端 P2P 直连的区别？

### 5. 哪些部署步骤未经实际验证？（Unverified Deployment Check）
- [ ] 由于只读边界未实际运行的构建/部署步骤（如多阶段 Docker 构建、外部 Nginx 配置、生产环境变量注入），是否已明确标记为静态分析或 `[待验证]`？
- [ ] 是否检查了多进程启动模式（如 Gunicorn `preload_app = False`）下，`lifespan` 启动钩子（如并发执行 `create_all` 或初始化任务）在多 Worker 并发启动时的竞争风险？

### 6. 哪些技术选型理由属于推测？（Speculative Rationale Check）
- [ ] 凡文档未声明、仅根据技术特性推导出的选型理由（如性能倍数对比），是否已明确标记为 `[逆向归纳]`？
- [ ] 是否检查了依赖配置文件（`pyproject.toml` / `package.json`）中是否存在重复声明、条件编译失效或未使用的幽灵依赖？

### 7. 哪些优化建议缺少明确收益依据？（Unfounded Optimization Check）
- [ ] 提出的性能瓶颈预警（如长轮询开销、队列 `LRANGE` 开销），是否结合了真实代码机制（如服务端内部 `sleep` vs 客户端请求）与业务约束（如单设备互斥下队列长度恒 $\le 1$ vs 固定队列积压）进行了准确量化？

### 8. 哪些通用方法只是简单改写原项目设计？（Superficial Rewrite Check）
- [ ] 检查 `reuse/REUSE_01..05` 中的参考代码：是否只是把原项目的表名/函数名改了个名字，却把原项目的局部缺陷（如无租约死锁、广播惊群、缺乏安全校验）一并照搬了过去？
- [ ] 是否已按照 `three-layer-extraction-guide.md` 执行了**缺陷升维重构**？

### 9. 哪些内容仍包含敏感或专有技术信息？（Sensitivity & Desensitization Check）
- [ ] `reuse/` 目录下是否 100% 清除了原项目的业务词汇、内部域名、内网 IP、特殊缩写与硬编码密钥？
- [ ] `internal/` 目录下引用的内网地址与管理接口路径是否已添加内部密级提示（且绝不包含明文密码/密钥）？

### 10. 哪些知识不足以支持后续工程维护？（Maintenance Readiness Check）
- [ ] 新接手工程师能否仅凭内部档案查到：① 全量环境变量字典；② 动态配置表（如 `system_config`）全量 Key 字典；③ 全量异步消息队列 Payload 字典；④ 资源死锁/卡死时的应急恢复 SOP？

### 2. 发现问题分级汇总（用于独立评审阶段输出）
- **严重遗漏（Critical）**：模型/状态机失真、核心链路遗漏、P0 级功能 Bug 或高危安全漏洞漏检。
- **重要问题（Major）**：机制误判、监控/报表细节偏差、跨项目方法论简单照搬未升维、维护字典缺失。
- **一般问题（Minor）**：次要模块细节简略、依赖声明瑕疵、敏感地址未打标签。
- **可选改进（Optional）**：前端路由表、CLI 辅助工具操作指南等锦上添花项。
