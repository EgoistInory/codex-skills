# “事实 → 原理 → 方法”三层知识萃取与净室重构指南

本指南服务于 `project-knowledge-extractor` 的 **Stage 5（Knowledge Extraction）** 与 **Stage 6（Clean-room Design）**。这两个阶段决定了复盘产出究竟是一份“换了变量名的原项目说明书”，还是一套真正能跨项目长期复用、合规且经过缺陷升维的工程方法资产。

---

## 一、三层知识升维转换表（How to Elevate from Facts to Methods）

每一个核心技术点都必须完成以下三级跳转换，严禁将第一层（事实）直接复制到 `reuse/` 目录中：

| 认知层级 | 核心追问 | 示例：设备池并发分配 | 示例：多进程高频读缓存 |
| :--- | :--- | :--- | :--- |
| **1. 事实层 (Facts)**<br/>*当前项目怎么做* | 具体哪个文件哪一行？用了什么表、什么 SQL、什么参数？存在什么 Bug？ | `app/crud/device.py:124-200` 使用 `FOR UPDATE SKIP LOCKED` 锁 `devices` 表，重试 5 次；但 `task.py:166` 取消运行中任务时未释放设备，且无租约超时字段，Worker 崩溃会导致设备永久卡在 `BUSY(1)`。 | `app/crud/project.py:16-154` 在每个 Worker 进程内存维护 `_cache` 字典，修改时向 `{ocr}project_cache:change` 发布 `"reload"`，所有 Worker 同时查库重载全表。 |
| **2. 原理层 (Principles)**<br/>*为什么有效及边界在哪* | 底层利用了数据库/OS 的什么原语？为什么比替代方案好？在什么条件下会失效？ | 利用 InnoDB 行级悲观锁的 `SKIP LOCKED` 跳过已锁行实现无阻塞并发抢占，利用 `ORDER BY updated_at ASC` 实现天然 LRU；但纯状态位锁属于“无租约锁（Unleased Lock）”，在持有者非正常消亡时缺乏自愈机制。 | 利用进程内哈希表实现 $O(1)$ 零序列化读取，利用 Python 引用赋值原子性实现无锁读切换，利用 Pub/Sub 实现最终一致；但全量广播触发全进程同时查库存在“惊群效应（Thundering Herd）”。 |
| **3. 方法层 (Methods)**<br/>*未来同类系统如何设计* | 如何剥离专有业务并**修补原项目缺陷**，形成标准可复用范式？ | **带租约自愈（Lease-Based）的 `SKIP LOCKED` 资源池模式**：在资源表设计中内建 `lease_until` 字段，抢锁条件升级为 `state='IDLE' OR (state='BUSY' AND lease_until < NOW())`，并在任务取消/终止终态转换时强制幂等释放。 | **带增量载荷或随机退避抖动（Jitter）的 L1+Pub/Sub 缓存模式**：小变更直接通过 Pub/Sub 消息体传递增量 JSON；全量重载时注入 `0~200ms` 随机退避或通过 Redis SingleFlight 避免多 Worker 同时冲击数据库。 |

## 二、Stage 5：工程设计决策 9 段式标准模板（`10_ENGINEERING_DECISIONS.md`）

在提炼 12 个维度（问题分析、需求拆解、技术选型、架构原则、模块划分、核心流程、状态与数据、错误处理、自动化测试、工程交付、运行维护、性能优化）的工程经验时，每条经验必须严格采用以下 9 段式结构：

```markdown
## 经验 N：[维度名称] —— [模式/方法一句话标题]

- **【工程问题】**：要解决什么普遍性的软件工程矛盾或痛点？（脱离当前业务名词描述）
- **【设计思路】**：为什么选择这种解决方向？核心权衡支点是什么？
- **【适用条件】**：在什么数据规模、读写比、团队规模或基础设施约束下值得采用？
- **【通用方法】**：其他项目可以怎样分步落地？（给出标准算法步骤或状态流转规则）
- **【优点】**：实质性解决了什么问题？带来了什么量化或架构收益？
- **【代价】**：增加了哪些实现复杂性、资源消耗或维护成本？
- **【局限】**：什么情况下绝对不适用或会退化失效？
- **【替代方案】**：行业内还有哪些备选设计？各自的分水岭在哪里？
- **【经验结论】**：可以沉淀成什么一句话通用架构原则（Rule of Thumb）？
```

## 三、Stage 6：净室设计蓝图规范（`REUSE_05_CLEAN_ROOM_BLUEPRINT.md`）

编写《从零设计同类技术系统的方法指南》时，必须遵守 **净室工程（Clean-Room Engineering）** 四项准则：

1. **领域场景中立化**：
   - 将原项目的具体业务场景（如某特定电商、特定游戏交易、特定内部平台）抽象为中立的通用技术场景（例如：“分布式边缘执行节点与异构计算资源调度中台”、“高并发异步作业编排与人机协同网关”）。
2. **数据模型与命名重构**：
   - 严禁沿用原项目特有的表名/字段名拼写瑕疵（如原项目混用 `is_TIM`、`qr_Url`、自由文本正则解析 `config` 等）。
   - 从零设计符合第三范式与现代工程规范的领域实体（例如使用强类型 JSON Schema 配置列、显式权限布尔列、租约过期时间戳 `lease_until`）。
3. **缺陷升维（Defect-Upgraded Implementation）**：
   - Stage 4 审计出的所有原项目架构隐患与安全漏洞（如导入期初始化崩溃、未鉴权路由、SSRF 漏洞、取消任务不释放资源、缺少数据库迁移管理），必须在 Clean-Room 蓝图中作为**正面示范（Built-in Safeguards）**给出正确的参考实现。
4. **自包含可落地性**：
   - 读者仅凭 `REUSE_01` ~ `REUSE_05` 这 5 篇文档，无需查看原项目任何一行代码，即可完整理解该类系统的架构全景、核心并发控制算法、选型依据与安全验收标准。
